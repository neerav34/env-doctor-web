Reference Manual

env-doctor

env-doctor is a static analysis tool for environment variables. It scans every source file in your project, extracts all process.env references (and equivalents in 7 languages), then cross-checks them against your .env and .env.example files. Discrepancies — missing variables, undocumented variables, unused variables, leaked credentials — are reported with exact file locations and fix suggestions.

It runs in milliseconds, requires zero configuration, and exits with codes CI pipelines understand. Nothing is sent to any server.

Why env-doctor

Environment variable problems are the number one cause of "works on my machine" bugs. The pattern is always the same: a developer adds process.env.SOME_NEW_KEY, forgets to add it to .env.example, the PR merges, a teammate pulls the branch and gets a cryptic runtime error, and thirty minutes of debugging later they realise the key was simply never set in their local .env.

The same problem shows up in production. A key is added in the code, the deployment script doesn't set it, and the app boots, runs for a while, and then crashes exactly when the code path that needs that key is first reached — sometimes hours later, sometimes in front of a user.

env-doctor solves this at three layers:

  • Development: the VS Code extension shows a squiggle on every undocumented env var as you type it.
  • Code review: the GitHub Action comments on every PR with a table of issues, so they're caught before merge.
  • Runtime: generate-validator writes a startup script that crashes immediately if any required variable is missing — before the rest of the app loads.

Installation

No install required to try it:

npx @neerav34/env-doctor check

Install globally to use as a plain env-doctor command:

npm install -g @neerav34/env-doctor

Install as a dev dependency to pin a version for your team:

npm install --save-dev @neerav34/env-doctor

Then add to package.json scripts:

"scripts": {
  "env:check":  "env-doctor check",
  "env:doctor": "env-doctor doctor"
}
💡

Node.js 18+ is required. env-doctor uses native fs/promises and Promise.allSettled.

Quick Start

Run from your project root. env-doctor finds your source files automatically:

terminal — my-project/
$ env-doctor check ERRORS (2) ✗ DATABASE_URL [Missing Required] DATABASE_URL is referenced in 2 location(s) but not defined in .env or .env.example └─ src/db.ts:14 const pool = new Pool({ connectionString: process.env.DATABASE_URL }); └─ src/migrate.ts:6 await migrate({ url: process.env.DATABASE_URL }); → Add DATABASE_URL to .env.example ✗ STRIPE_SECRET_KEY [Missing Required] └─ src/api.ts:5 const stripe = new Stripe(process.env.STRIPE_SECRET_KEY); → Add STRIPE_SECRET_KEY to .env.example WARNINGS (2) ⚠ OLD_API_KEY [Unused Variable] OLD_API_KEY is defined in .env but never referenced in source code → Remove OLD_API_KEY from .env or check for typos ⚠ REDIS_URL [Example Drift] REDIS_URL exists in .env but is missing from .env.example → Run `env-doctor check --fix` to sync .env.example Scanned 47 files in 38ms · 2 errors · 2 warnings

Auto-fix — updates .env.example to match what the code actually references:

env-doctor check --fix

Scan Pipeline

Every command (check, doctor, init) runs the same five-stage pipeline. Understanding it helps you predict what env-doctor will and won't catch.

01
Discover
Glob source files, respect .gitignore and ignore patterns
02
Filter
Skip binary files by checking for null bytes in first 1 KB
03
Detect
Run regex patterns against every file, record exact line + column
04
Parse
Read .env and .env.example into key→definition maps
05
Analyze
Cross-reference all three maps, produce typed issues

Stages 02 and 03 run in parallel across all files using Promise.allSettled. A single unreadable file never aborts the scan — it's counted as skipped and the rest continue.

File Scanner

The scanner's job is to produce a list of source files worth analysing.

What it includes

It globs the project root recursively for all files, then respects your .gitignore (when present). The default ignore list is:

node_modules/**
.git/**
dist/**
build/**
.next/**
.nuxt/**
coverage/**
*.min.js
*.map

Additional patterns can be added via --ignore or the ignore key in .env-doctor.json.

Binary detection

After globbing, each candidate file is checked for binary content before being read fully. The scanner opens the file, reads the first 1,024 bytes, and checks whether any byte is a null byte (0x00). If null bytes are found, the file is classified as binary and skipped. This handles images, compiled outputs, lock files, and archives — none of which would contain meaningful env var references anyway.

// scanner.ts — binary detection
const buffer = Buffer.alloc(1024);
const { bytesRead } = await fd.read(buffer, 0, 1024, 0);
// Null bytes mean binary → skip
return !buffer.subarray(0, bytesRead).includes(0);

Detector

The detector runs a set of language-specific regex patterns against each file's content. Every match produces an EnvVarReference object with the variable name, file path, line number, column number, language, and surrounding source line for context.

Comment skipping

Before recording a match, the detector checks whether the line is commented out. A line is considered a comment if it starts (after trimming whitespace) with //, #, *, /*, --, or <!--. Commented references are silently ignored.

Deduplication

The detector uses a Set<string> keyed on varName:line:column. If two patterns both match the same variable at the same position, only one reference is recorded.

Destructuring (JS/TS)

A separate pass handles const { VAR1, VAR2 } = process.env. The destructure body is split on commas, and each part is further split on : or = (to strip aliases and defaults) to extract the original key name. Only names matching /^[A-Z_][A-Z0-9_]*$/ are recorded.

// All forms are handled:
const { PORT, NODE_ENV } = process.env
const { PORT: port, NODE_ENV: env = 'dev' } = process.env
let   { API_KEY, SECRET_KEY } = process.env

.env Parser

The parser reads both .env and .env.example into a Map<string, EnvVarDefinition>. It handles the full range of .env syntax found in real projects.

What the parser handles

SyntaxExampleParsed value
Bare assignmentPORT=30003000
Double-quotedNAME="John Doe"John Doe
Single-quotedMSG='hello world'hello world
Shell export prefixexport KEY=valuevalue
Inline commentPORT=3000 # HTTP port3000
Empty valueFEATURE_FLAG=empty string
Multiline (quoted)CERT="line1↵line2"two-line string
Comment lines# this is a commentskipped
Blank linesskipped

Key validation

Only keys matching /^[A-Za-z_][A-Za-z0-9_]*$/ are accepted. Invalid keys (spaces, hyphens, leading digits) are silently skipped.

Value truncation in output

When displaying values, env-doctor shows only the first 3 characters followed by ***. A value sk_live_abc123xyz displays as sk_***. The full value is retained internally for audit's secret detection — truncation is display-only.

Missing files

If .env doesn't exist, the parser returns an empty map and continues — this is normal in CI. If .env.example doesn't exist, env-doctor recommends running env-doctor init first.

Analyzer

The analyzer receives three maps — code references, .env definitions, .env.example definitions — and produces a sorted list of typed issues.

Decision matrix

In code?In .env?In .env.example?Result
yesnonoERROR Missing Required
yesnoyesWARN Missing Optional (not set locally)
yesyesyes✓ Clean
yesyesnoWARN Example Drift (undocumented)
noyes—WARN Unused Variable
nonoyesWARN Example Drift (stale example entry)

Browser exposure check

If the analyzer detects Next.js or Vite, it flags any variable with a NEXT_PUBLIC_ or VITE_ prefix that looks like a secret name as ERROR browser-exposure.

Sort order

Issues are always sorted: errors first, then warnings, then alphabetically by variable name within each group.

doctor

Runs the full scan and produces a health score (0–100) plus trend analysis vs. previous runs. History is stored in .env-doctor/cache.json.

env-doctor doctor [options]

Accepts the same options as check.

Health score algorithm

76
score = max(0, 100 − (errors × 10) − (warnings × 3))
Example: 2 errors + 2 warnings → 100 − 20 − 6 = 74

generate-validator

Generates a startup script from your .env.example. Every key in the example file becomes required. If any are missing at runtime, the app crashes immediately with a clear list before anything else loads.

env-doctor generate-validator [options]

Options

--example-file <path>
default: .env.example
Source file — every key here becomes required
--output <path>
env-validator.js
Output file path
--typescript
Generate a .ts file instead of .js
--root <path>
default: cwd
Project root directory

Generated file

// Auto-generated by env-doctor — do not edit manually
// Re-generate: npx @neerav34/env-doctor generate-validator

const REQUIRED_ENV_VARS = [
  "DATABASE_URL", "JWT_SECRET", "SESSION_SECRET", "PORT", "NODE_ENV"
];

const missing = REQUIRED_ENV_VARS.filter((key) => !process.env[key]);

if (missing.length > 0) {
  console.error('[env-doctor] Missing required environment variables:');
  missing.forEach((key) => console.error(`  - ${key}`));
  console.error('[env-doctor] Add them to your environment and restart the app.');
  process.exit(1);
}

Wire it into your entry file

CommonJS
require('./env-validator.js'); // ← must be line 1, before everything
const express = require('express');
ESM / TypeScript
import './env-validator.js'; // ← must be line 1
import express from 'express';

What failure looks like

node index.js (missing DATABASE_URL)
[env-doctor] Missing required environment variables: - DATABASE_URL - JWT_SECRET [env-doctor] Add them to your environment and restart the app.
⚠

Commit env-validator.js to your repository — do not gitignore it. The file contains no secrets; it's only a list of required key names. Every deployment environment needs it at startup.

VS Code Extension

Inline squiggles on every process.env.VAR not in .env.example — as you type, no terminal needed.

Search env-doctor in the Extensions panel or: Marketplace →

How it works

On activation the extension creates a DiagnosticCollection and a FileSystemWatcher on **/.env.example. Any change to that file re-runs on all open documents. For each JS/TS document it:

  1. Walks up from the file's own directory to find .env.example (handles multi-root workspaces).
  2. Parses the file into a set of known keys.
  3. Runs the same detection patterns as the CLI — dot notation, bracket notation, destructuring.
  4. Creates a vscode.Diagnostic for each reference not in the known-keys set.

Settings

envDoctor.exampleFile.env.exampleFilename to look for when walking up from each open file
envDoctor.enabledtrueDisable all diagnostics without uninstalling

Monorepo

With --monorepo, env-doctor discovers each package directory (by finding package.json files) and scans them independently — each against its own .env* files.

env-doctor check --monorepo
env-doctor doctor --monorepo

Multi-env variants are auto-discovered per package: .env.local, .env.staging, .env.production are all merged when computing what's defined.

💡

You can target a single package from the repo root with --root packages/api without --monorepo.

All clear — no errors, no warnings
1

2

The distinction between 1 and 2 lets you fail hard on errors while surfacing warnings without breaking CI. Use --strict to collapse both to 1.

Troubleshooting

env-doctor reports nothing but I know there are issues

Make sure you're running from the correct directory — env-doctor scans from cwd by default. Use --root if your source files and .env.example are in different directories. Also confirm the file extension is one env-doctor knows about (see Detection Patterns).

Lowercase variable names aren't detected

By design. env-doctor only matches /^[A-Z_][A-Z0-9_]*/. The convention for env vars is uppercase — matching lowercase would produce too many false positives from JS object properties.

A variable shows as missing but it's in .env.example

Check the key name character by character — one typo breaks the match. Confirm the line isn't commented out (#) and that the format is valid (KEY= or KEY=value). A space before = on the key side (KEY =value) is not valid — the parser requires KEY=value.

VS Code extension isn't showing squiggles

Open the Output panel (⇧⌘U) and select env-doctor from the dropdown. The extension logs every scan there. Common causes: the extension hasn't activated (open a .ts or .js file), or .env.example wasn't found (check the log to see what path it found). After adding a variable to .env.example, save the file to trigger a re-scan.

Too many false positives from shell scripts or Dockerfiles

{ "ignore": ["scripts/deploy/**", "*.sh"] }

generate-validator crashes on prod but not locally

The validator checks process.env at module-load time. On most cloud platforms (Railway, Render, Heroku, Vercel) env vars are injected before Node starts — the validator should work. If you're using a container platform with a CMD entrypoint, check that env vars are available before the process starts, not injected after.
